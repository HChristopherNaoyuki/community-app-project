## Document Purpose

This document provides complete, professional documentation for the
Community Safety, Health, and Wellness App repository.

tracking method, and instructions for use.

It also defines the writing, formatting, and media standards that
apply to all files in this repository.

## Project Overview

This repository was created for IPMA6212 Assignment 2, Question 3.2.

It demonstrates the use of GitHub for project management, version
control, and issue tracking within a community-driven mobile
application project.

The project focuses on designing and planning a cross-platform mobile
app that enhances community safety, promotes wellness, and improves
access to emergency information.

Each GitHub issue corresponds to a specific task or deliverable
identified in the Work Breakdown Structure (WBS) from Question 2.

## Issues Log Structure

The GitHub Issues Log is the main tool used to manage all project
tasks and deliverables.

Each issue follows a consistent structure. The fields are described
below.

### Issue Name

A short description of the task or deliverable.

### Assignee

The group member responsible for completing the task.

### Labels

The category of the issue, such as design, backend, or documentation.

### Project

The main project board that tracks all work.

### Milestone

The stage of completion or the related project phase.

### Purpose of This Structure

This structure helps the team monitor progress, assign
responsibilities, and maintain accountability throughout the project.

## How to Use This Repository

Follow the steps below to work with the repository.

1. Go to the **Issues** tab to view and manage tasks.
2. Filter issues by **Labels** or **Milestones** to organise tasks by
   category or phase.
3. Open the **Projects** tab to view the Kanban board for progress
   tracking.
4. Update the issue status as work moves from "To Do" to "Done."
5. Add comments, assign tasks, or close issues when they are
   completed.

### Recommended Workflow

- Review open issues at the start of each work session.
- Update the status of any issue you are working on.
- Comment on issues when you need input from other team members.
- Close issues only when the deliverable is complete and reviewed.

## Writing and Formatting Standards

All documentation in this repository must follow the standards below.

### Language and Tone

- Use simple, clear business English.
- Keep the tone formal, professional, and academic.
- Write in a direct and straightforward manner.
- Avoid unnecessary complexity and ambiguity.

### Punctuation

- Do not use em dashes or en dashes.
- Use commas, parentheses, or other suitable punctuation instead.

### Accuracy and Sources

- Base all statements on verified, factual information.
- Do not speculate, guess, or present opinions as fact.
- State clearly when something cannot be confirmed.
- If a textbook is provided, use it as the sole source of information.

### Structure

- Keep content logical and coherent.
- Use headings and subheadings to organise information.
- Include a Table of Contents where required.
- Link every Table of Contents entry to its section.

### Code Formatting

- Use Allman style for all code, with opening braces on new lines.
- Include detailed comments that explain logic and functionality.
- Write comments for an intermediate-level audience.

## Visual Media Policy

All visual content must follow the rules below.

- Do not place images or emojis directly in documentation files.
- Store all visual media in a dedicated folder in the project
  directory.
- Name the folder clearly to show it contains visual content, for
  example `images`, `screenshots`, or `media`.
- Keep the folder well structured and easy to navigate.

This policy keeps documentation files clean, portable, and easy to
maintain.

## Support and Issue Reporting

If you find a problem or error, follow the steps below.

- Do not attempt to fix the problem silently or outside the project.
- Submit a pull request on the GitHub repository.
- Or open an issue on the GitHub repository.

This allows the maintainers or contributors to review and address the
problem in a controlled and transparent way.
